## Blockers

### QA-001: Six storefront pages show "We couldn't load this page" on a direct load or refresh
- **Area:** storefront
- **URLs:** `/inventory`, `/financing`, `/trade-in`, `/test-drive`, `/service`, `/compare` (also any query-string version, such as `/inventory?make=BMW`, when opened directly)
- **Steps:** Open any of these URLs in a fresh tab, or press refresh while on one.
- **Expected:** The inventory list, the financing, trade-in, test-drive and service forms, and the compare page.
- **Actual:** A blank page with "ERROR / We couldn't load this page. / Retry". The header and footer are missing. The `<title>` is just "Inventory" with no store-name suffix, which means `loadStorefrontBusiness()` returned `status: 'error'`. The response headers are `x-nextjs-prerender: 1`, `x-nextjs-cache: HIT` and `cache-control: s-maxage=31536000`. The error state was prerendered at build time, when the GraphQL/DB call failed, and is now cached for a year. "Retry" serves the same cached HTML. The pages only render when reached by client-side navigation from another page, such as the footer links (verified: "On the lot", "Book a test drive", "Book service", "Payment estimate", "Trade-in review"). So every shared link, ad click, Google result, bookmark or refresh lands on an error.
- **Likely files:** `app/(storefront)/inventory/page.tsx`, `financing/page.tsx`, `trade-in/page.tsx`, `test-drive/page.tsx`, `service/page.tsx`, `compare/page.tsx`. None of them set `export const dynamic = 'force-dynamic'`; `page.tsx` (home) and `photo-credits/page.tsx` do. The root cause is `app/(storefront)/layout.tsx` together with `features/storefront/lib/data/storefront-business.ts`: the layout fetches store settings and allows static prerendering, and the error result is cacheable. Make the storefront layout dynamic, or at least never let the error branch be prerendered or cached.

### QA-002: The public storefront shows 0 vehicles while the desk shows 3 approved, available units
- **Area:** storefront and dashboard
- **URLs:** `/` ("0 IN STOCK", "No vehicles listed"), `/inventory/cmtyk8263000lmv0xmjtm22du` ("Vehicle not found"), `/dashboard/platform/vehicles`
- **Steps:** Open Dashboard → Inventory. All 3 units (BMW 530i, Toyota Highlander, Mach-E) show `AVAILABLE · ACQ FRONTLINE · RECON COMPLETED · MERCH APPROVED`. Then open the storefront, or query `publicInventoryVehicles` (it returns `totalCount: 0`).
- **Expected:** A unit the desk calls approved and available is listed publicly. If it can't be, the desk says why and offers a fix.
- **Actual:** All 3 `InventoryStock` rows have `approvedRevisionHash: ""`. `queryPublicInventory` filters on `approvedRevisionHash: { not: '' }`, and `assertPublishableInventory` errors are swallowed silently, so the storefront is empty. The desk still shows "MERCH APPROVED" and hides the Submit/Approve button once a unit is approved (`merchandisingStatus !== 'approved'`). That leaves no UI path to re-approve and publish these units. "Publish feed" doesn't help either. A real Approve does write a hash: my QA unit got one (see QA-003).
- **Likely files:** `features/keystone/integrations/inventory/publicStorefrontInventory.ts:118-145`, `features/keystone/lifecycle/inventoryPublication.ts:60`, `features/platform/vehicles/screens/VehicleListPageClient.tsx:708-712`. Backfill the hash for seeded or approved rows. Also make the desk flag units that aren't publicly live ("Not live: approval evidence missing"), with a re-approve action.

### QA-003: Recon can't be advanced, so no newly intaken vehicle can ever be published
- **Area:** dashboard
- **URL:** `/dashboard/platform/vehicles`
- **Steps:** Intake a vehicle (`QA-001`). Click **Begin recon**, which moves the acquisition to reconditioning. Click **Open recon** and enter a work item and cost, which saves. Click **Advance recon**.
- **Expected:** The work item goes to in-progress, then completed. Then Mark frontline and Approve make the unit public.
- **Actual:** The banner says "We couldn't confirm the recon was started. Retry to finish." Retry fails the same way. Calling the same mutation `transitionInventoryReconWorkItem(id, toStatus:"in-progress", expectedUpdatedAt:<exact value>)` returns GraphQL `"Unexpected error."`. It returns the same message when `expectedUpdatedAt` is deliberately stale, so it fails before the optimistic-lock check, and the real reason is hidden from the merchant. The UI only offers "Complete recon" once a work item is `in-progress` (`advanceRecon`), so recon can never complete. **Mark frontline** then answers "Complete recon and approve the listing before marking this vehicle frontline." Together with QA-002, the storefront has no working path to list any vehicle.
- **Likely files:** `features/keystone/mutations/inventoryStockCommands.ts:187-216` (`transitionInventoryReconWorkItem`). Suspects: the `context.query.InventoryReconWorkItem.findOne` with nested `stock { rooftop { id } }` access, `assertSessionRooftopPermission`, or the `commandEvent`/`stockEvent` writes. Check the Railway logs for the stack. Client: `features/platform/vehicles/screens/VehicleListPageClient.tsx:375-409`. Also consider surfacing server error text instead of "Unexpected error.".

## Major

### QA-005: Intake can't record condition, trim or colours, so every unit becomes "Used"
- **Area:** dashboard
- **URL:** `/dashboard/platform/vehicles` → Intake
- **Steps:** Open Intake. The fields are VIN, stock #, year, make, model, odometer, purchase cost, retail price, lot location, description and photo URL.
- **Expected:** A dealer can intake New, Certified or Used units with trim, exterior and interior colour, and features (the `IntakeInventoryVehicleInput` API already accepts `trim`, `exteriorColor`, `interiorColor`, `condition`, `features`). Make should come from the Makes list. Photos should be uploadable rather than typed as a URL.
- **Actual:** Condition is hard-coded to `'used'`. Trim and colours can't be entered (the deal page shows "Color -"). Make is free text. The storefront's New and Certified filters can never match an intaken unit.
- **Likely files:** `features/platform/vehicles/screens/VehicleListPageClient.tsx:251` (`condition: 'used'`), `features/platform/vehicles/actions/index.ts:93`.

## What worked
- Admin sign-in, plus the customer sign-up, sign-in, profile and access-denied flows.
- All 103 dashboard links return 200, with no horizontal overflow at 390 px on the platform desks.
- Contact form (`INQ-T4WHFTTJ`), which appears as a CRM lead with notes. Service booking (`SVC-IVRA03AE`), which appears in service appointments. Test drive request (`TD-X45DXR1T`), which can only be reached by client-side navigation (QA-001).
- Intake VIN validation (it rejects I, O and Q).
- Merchandising Submit and Approve, which write a proper approval hash.
- Deal creation, the worksheet versioning and the 6/8 checklist.

## Not covered
- Stripe checkout: the storefront has no payment step (deposits and reservations are absent; a dealership would want a refundable deposit on a VDP).
- The VDP, compare and the full inventory filter UI with real cards, because no vehicle is publicly listed (QA-002, QA-003).
- The financing application and trade-in submissions: the forms render by client-side navigation but were not submitted.
