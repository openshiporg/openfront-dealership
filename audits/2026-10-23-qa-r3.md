## Blockers

### QA-R3-001: Recording payment on a cash deal always fails, so cash deals can't be delivered
- **Area:** dashboard
- **URL:** `/dashboard/platform/finance` (deal `cmvlnzxt0001jnv0xnqt1ssj0`)
- **Steps:**
  1. Create a cash deal (Camry QA-002, $32,900, $1,000 down).
  2. Save the worksheet, present it, accept, submit and approve.
  3. On Finance, record the identity, OFAC and privacy checks and the signed buyer's order.
  4. Click **Record payment**. The amount is prefilled at $34,785.06. Enter a receipt reference, tick "Payment received in full" and click Save.
- **Expected:** The payment is recorded, a captured `PaymentTransaction` is created, and "Release to delivery" becomes the next step.
- **Actual:**
  - The dialog shows "Domain event idempotency key was reused with different evidence", every time.
  - It reproduced 3 times, each on a fresh page load with a new `finance-operator:<uuid>` key:
    - with the auto-declined menu;
    - after a rejected $1,000 partial attempt;
    - after presenting and declining the F&I menu by hand.
  - The request sent is `manageFinanceFundingCase { status: 'funded', paymentAmountCents: 3478506, checklist: [payment-received], idempotencyKey: 'finance-operator:6a0fcafe-…' }`. The response is `{"success":false,"error":"Domain event idempotency key was reused with different evidence","rejected":true}`.
  - Nothing is saved. Read-only GraphQL shows:
    - no `FinanceFundingCase` or `PaymentTransaction` for the deal;
    - no domain audit event containing `cash-payment` or the request's UUID.
  - So the colliding event exists only inside the failing transaction.
  - The deal stays "approved" and the Camry stays "pending" (off the storefront) indefinitely.
- **Likely files:**
  - `features/keystone/mutations/financeOperations.ts:178-243` (`manageFinanceFundingCaseCommand`, cash branch);
  - `:253-280` (`recordCashSalePrerequisites`, which records `finance-prerequisite-review:cash-payment:<key>`);
  - `features/keystone/lifecycle/domainEvents.ts:54-79` (where the error is raised).
- **What to look for:** Within one transaction, something calls `recordDomainEventInTransaction` twice with the same `eventKey` and different payloads. Or the transaction callback runs twice (for example a serialization retry) and the second run hashes a new `now` timestamp. I couldn't pin it down from the code. Reproduce it locally against a cash deal with a doc fee and tax line. This path was never runtime-tested (round-2 fix notes: "untested at runtime").

### QA-R3-002: Customer account page crashes (HTTP 500) as soon as the customer has any request
- **Area:** storefront
- **URL:** `/account`
- **Steps:**
  1. Create an account.
  2. Book a service at `/service` (or submit any test drive, trade-in or financing request while signed in).
  3. Open `/account`, or sign out and sign back in.
- **Expected:** The account overview with the request history ("Service · Confirmation pending · SVC-UDGYPNPW").
- **Actual:**
  - "This page couldn't load. A server error occurred." HTTP 500 and React error #441.
  - Sign-in redirects to this crash, so the customer's account is unusable.
  - `/account/profile` still loads.
  - The GraphQL data is fine: `customerRequestHistory` returns `{kind:"Service", scheduledAt:"2026-10-26T15:00:00.000Z", status:"scheduled", timezone:"America/Chicago"}`.
- **Cause (confirmed):** `formatRequestTime` passes `dateStyle`/`timeStyle` together with `timeZoneName`. `Intl` forbids that combination and throws `TypeError: Invalid option`. The `catch` retries with the same combination, so it throws again during the server render. Round 2 only saw an account with no requests, so the list never rendered.
- **Likely file:** `features/storefront/screens/AccountPage.tsx:35-42`. Drop `timeZoneName`, or use explicit `month/day/year/hour/minute` fields, which can be combined with `timeZoneName`.
